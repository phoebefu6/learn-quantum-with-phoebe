The data-loading fine print

Session 2 watched a search find one item in about the square root of N oracle calls, and it was real. It also assumed something the vendor deck never says out loud: that the data was already inside the machine. Brindle's 12 million customer rows live on disk, and every one of them has to be written into quantum memory before the first query runs. Tonight prices that write, with the four caveats Aaronson published in 2015, the one claim the best qRAM design does and does not make, and a calculator in the page that prints the load beside the search. No machine, vendor or roadmap is named.

Part 0

The sentence that leaves something out

Brindle is a constructed retailer with a 12-million-row customer table, a 4-million-row order table and twenty years of encrypted backups. Page four of the vendor deck says the pilot will "search all 12 million customers at quantum speed". The sentence is not false. The search half of it is the arithmetic session 2 measured. What it leaves out is the step before the search, and the leader's job tonight is to find that step, put a number on it, and rewrite the sentence so it contains both halves.

Live = presented in the 45 minutes Self-study = the full depth, after class 🔍 Every diagram zooms

★ What you walk out with tonight. Aaronson's four caveats in his order, each with what it means for a table you own. The one claim the qRAM paper makes, and the one it never makes. A number for Brindle's single search, quantum against classical, with the model's three parameters printed beside it. A window, in searches per load, inside which the quantum route is ahead and outside which it is not. And one honest sentence to replace the deck's.

LiveRead the deck's sentence slowly3 min▶

"Search all 12 million customers at quantum speed." Split it into the work it implies. First, the 12 million customers have to become something a quantum search can query: an oracle that can be asked about any row, in superposition. Second, the search asks that oracle about the square root of N times. Third, a measurement returns one row. The sentence describes the second step and is silent on the first and third.

Silence on the first step is the expensive one. A search is fast because it touches far fewer than N rows. Loading touches every row once, by definition, because a row that was never written cannot be found. So the moment the data starts outside the machine, the job contains an order-N step, and an order-N step is exactly what the square-root speedup was supposed to avoid.

Real world

Brindle's data engineering lead, reading the constructed deck, asked the question an engineer always asks about a new store: how does the data get in, and how long does that take. The deck had no page for it. Every pitch that promises a fast query over a big table owes you an ingest number, and a quantum pitch owes it more, because the query is the only part it can speed up.

Self-studySix words for tonight3 min▶
  • Load. Writing N classical values into quantum memory. One write per row, so N writes for N rows. The step the deck skips.
  • Query. One call to the memory to read a value, or a superposition of values, at an address. What qRAM is designed to make cheap.
  • Oracle. The gate that marks the row being searched for. Session 2 treated it as free. Tonight it costs one query, and the query costs something.
  • qRAM. Quantum random access memory: n qubits of address reaching N = 2 to the n cells at once. Proposed by Giovannetti, Lloyd and Maccone in 2008; part 2.
  • Fine print. The conditions a speedup depends on, mostly about getting the data in and the answer out. Aaronson's word, and the stance of these sessions.
  • Searches per load. How many times the loaded memory is searched before the data changes and has to be loaded again. Written R. The one number that decides who wins.
Self-studyWhat tonight does not do2 min▶

Tonight prices the load with a declared model, not a machine. No qRAM of the size Brindle would need has been built, so there is no measured write time to quote, and none is invented. The hardware cost of building such a memory is not taught; nobody on the hub teaches hardware.

The linear-systems algorithm Aaronson's essay was written about, HHL, is named so the caveats make sense and is not taught. Session 4 picks up the second half of his argument: what happens when the fine print is satisfied and a classical algorithm turns out to need the same fine print and runs nearly as fast.

Part 1 · covers Aaronson 2015, four caveats

Four caveats, and the first one is a load

15 min live

In 2015 Scott Aaronson wrote a short essay in Nature Physics titled "Quantum machine learning algorithms: read the fine print". It lists four conditions under which the best-known quantum linear-algebra speedup holds, and shows that any one of them can eat the speedup whole. The first is about getting the input in. The drawing below is that first caveat, applied to the search the deck is promising.

LiveThe four caveats, in Aaronson's order6 min▶

Aaronson wrote about HHL and its offshoots, the algorithms that promise an exponential speedup for linear algebra. Each caveat below can kill that speedup on its own. Read each one twice: once as he wrote it, once as a question about a table you own.

  • 1. The input has to be loaded fast. That needs a quantum RAM and a reasonably uniform vector, and if preparing the input already takes n to some power steps, the speedup vanishes "in the very first step". For a data table: if the rows start on disk, somebody pays to write them in, and that payment is order N.
  • 2. Applying the matrix has to be fast. That needs the matrix to be sparse or to have structure. For a data table: a dense customer-by-product matrix with no structure does not qualify just because it is big.
  • 3. The matrix has to be well conditioned. Run time grows about linearly with the condition number. For a data table: a nearly collinear feature set, the kind every analyst has met in a regression, is the bad case.
  • 4. Reading the output costs about n repetitions. The answer is a quantum state, not a list of numbers, and reading one specific entry takes about n runs. For a data table: if the business wants the whole answer column back, the readout alone can cost what the classical method cost.

A search claim like the deck's is not a linear-systems claim, so caveats 2 and 3 do not apply to it directly. Caveats 1 and 4 apply to anything that starts and ends in classical data, which is everything a data team owns. Tonight prices caveat 1; caveat 4 is why the deck's single returned row is a measurement, which session 1 already taught you to read as a sample.

LiveHis general rule, and the two-part check4 min▶

Aaronson states the condition for an exponential speedup in one sentence with two halves. There must be an extremely fast way to create a certain superposition, AND there must be no fast way to create the analogous probability distribution classically. The first half is caveat 1 restated. The second half is the one most decks never test.

His worked example makes the second half concrete. An inner-product estimate from Lloyd, Mohseni and Rebentrost runs in about log(mn) over epsilon quantum steps. Under the same uniformity condition the quantum algorithm needed, a classical sampler does the same job in about log(mn) over epsilon squared. The gap is at most quadratic, not exponential, and the condition that made the quantum version fast is what made the classical version fast too.

His closing position is the stance these sessions adopt, and it is a check any leader can run: for each application, (a) does it satisfy all of the fine print, and (b) once the fine print is included, does a fast classical algorithm give the same information. Session 4 is a published case where the answer to (b) turned out to be yes.

Self-studyThe bridge to search: why a single 1 cannot be loaded for free4 min▶

A footnote in the essay connects his linear-algebra fine print to the search fine print. If HHL could take, as input, a vector that is a single 1 with zeros everywhere else, and prepare it fast without knowing where the 1 was, it would find that 1 faster than the Bennett-Bernstein-Brassard-Vazirani bound allows for black-box search. That bound is the same one Grover's algorithm sits at, about the square root of N queries, and nothing can go below it.

Read it from the data side. Finding the one row with a 1 in it is a search. Loading a vector that already has the 1 in the right place means somebody already knew where the row was. So a fast load of arbitrary classical data would be a faster-than-possible search in disguise, and a load of N rows that the machine does not already know costs order N. A square-root search gain cannot survive an order-N load.

A second footnote is about what qRAM is allowed to be. It has to be passive. A memory that needed a parallel processing element for every stored number would let a classical parallel machine solve the same linear system in about log squared n too, and then the comparison would be quantum against a very wide classical computer, not quantum against your warehouse.

Real world

Brindle's constructed deck promises the search and, two pages later, a "quantum-accelerated recommendation model". Run the four caveats on each and they fail differently. The search fails caveat 1 at the first step: the 12 million rows are on disk. The recommendation claim needs caveats 1, 2, 3 and 4 all satisfied before it is worth testing, and then it needs check (b), which is session 4's whole subject.

Part 2 · covers qRAM and the one-search arithmetic

qRAM cuts the query and never the write

10 min live

The serious answer to caveat 1 is a quantum memory. Giovannetti, Lloyd and Maccone proposed one in 2008: n qubits of address reach N = 2 to the n cells, and their design needs about log N switches per memory call instead of the N a conventional design would use. That is a real improvement, to the query. The drawing shows where it stops.

LiveWhy one search over fresh data always loses4 min▶

Set the widget to 12,000,000. Under the declared model (load 1 per row, query cost log2 N per oracle call, one search per load) the quantum route costs 12,063,988: 12,000,000 to load and 63,988 to search. A classical brute-force scan, Grover's own N over 2, costs 6,000,000. The quantum route is about twice as expensive, and the whole of the difference is the load.

Now move N through every option and watch the verdict. It never changes, and the reason is one line of algebra rather than a coincidence of these sizes. Loading costs N. Brute force costs N over 2. N is bigger than N over 2 for every N, so the load alone has already lost before the first query runs, and the square-root search gain, however large, is spent on a race that ended at ingest.

This is caveat 1 with a number on it. It does not say quantum search is a mistake. It says a quantum search over data that starts on disk and is searched once is a slower way to do a scan.

LiveLoad once, search R times: the window4 min▶

The load is paid once per load. If the memory is searched R times before the data changes, the load is shared across R searches, and the comparison shifts. Under the same model, quantum beats brute force from R = 3 on every table from 10,000 rows up (from R = 4 at 1,000 rows), because three scans at N over 2 each cost more than one load plus three short searches.

But if Brindle is going to search the same table thousands of times, nobody honest compares against a brute-force scan. A data team would build an index once, at about N log2 N, and then answer each search in about log2 N. Against that baseline the quantum route stays ahead only while R is small enough that building the index has not paid for itself. On 12,000,000 rows that ceiling is 4,224 searches per load.

Self-studyThe model is declared, not measured3 min▶

Every number in the widget and the table comes from three parameters, and all three are choices. Load cost 1 per row says a write into quantum memory costs the same as one classical lookup, which is generous: no qRAM of this size exists to time. Query cost log2 N per oracle call takes the 2008 design at its word, about log N switches per memory call. Searches per load, R, is whatever the use case says it is.

Move any of them and every column moves. A dearer write pushes the brute-force crossover up. A dearer query shrinks the window from the top. Practitioner session 6 is a calculator that exposes all three as sliders; tonight they are fixed so the argument has one shape. What none of the parameters can do is make one search over fresh data win, because that needs a load cheaper than half a row per row, and that is the write qRAM never promised.

Real world

Brindle's constructed customer table is refreshed nightly from the order system. If the pilot's search runs ten times a day, that is R = 10 per load, inside the window. If it runs once, it is outside, and the scan wins. The same deck, the same machine, the same table: the answer turns on a scheduling fact that only Brindle's data team knows, which is why the deck could not have answered it.

Part 3 · build-along

Rewrite the deck's search sentence

17 min hands on

No code. Six steps with the widget above and the deck's sentence from Part 0. The aim is to leave with one sentence a board can read, which contains the load, the search and the window, and one question for the vendor.

Copy the sentence exactly

"Search all 12 million customers at quantum speed." Write it at the top of a page, word for word. Rewriting starts from what was actually claimed, not from what you assume was meant.

Mark which caveats it skips

Go through Aaronson's four in order. Load the input: skipped, the rows are on disk and the sentence is silent. Apply the matrix fast and well conditioned: not a linear-systems claim, so mark them not applicable. Read the output: one row comes back as a measurement, so ask how many runs are needed to trust it. Write the caveat numbers in the margin.

Take the 12,000,000 row from the widget

Quantum, one search: 12,063,988. Classical brute force: 6,000,000. Copy the three model parameters next to them, exactly as the widget prints them: load 1 per row, query cost log2 N per oracle call, R = 1 search per load. A number without its parameters is the same mistake the deck made.

Note the search-only number, and say what it is

Indexing 12,000,000 rows needs 24 qubits, since 2 to the 24th is 16,777,216. Over that full index space a search takes about 3,217 oracle calls against 8,388,608 classical lookups for an even chance, a factor of about 2,600. These three numbers are closed-form arithmetic, not a simulation: 24 qubits is past the simulator in this page. This is the number the deck is quietly quoting. The widget's 2,721 counts the 12,000,000 rows themselves; both leave out the load.

Write the honest sentence

Something like: "Once our 12 million rows are loaded, which costs about 12 million writes, a quantum search beats a full scan only if we search the loaded table between 3 and 4,224 times before reloading it; below that a scan wins and above it a classical index wins. This is a declared model, not a measurement." Shorten it if you can; do not drop the window or the word model.

Write one question to send the vendor

One question, in writing, with a number in it. "What does loading our 12 million customer rows cost, in writes and in hours, and how many searches per load does your pilot plan assume?" If the reply gives a search time and no load time, you have learned the most useful thing the reply could tell you.

The habit to keep. Ask what the load costs before you ask what the search costs. A fast query over data that has to be written in first is only as fast as the write, and the write is the page a pitch is most likely to leave out.

Check yourself

Three questions

Under the declared model, one quantum search over a freshly loaded table always costs more than a classical brute-force scan, at every table size in the widget. Why?

A · Because each oracle call is slower than a classical lookup, and there are too many of them
B · Because loading N rows costs N, which is already more than the N over 2 lookups a scan needs; the square-root search gain is spent before the first query runs
C · Because a quantum memory large enough does not exist yet
The oracle calls are the cheap part: 63,988 against a 12,000,000 load on Brindle's constructed table (load 1 per row, query cost log2 N, one search per load). The loss is structural, N against N over 2, and it holds whatever the size. C may be true but is not the reason; the model assumes the memory exists and the search still loses.

Giovannetti, Lloyd and Maccone's 2008 qRAM design is often cited as the answer to the loading problem. What does it reduce, and what does it leave alone?

A · It reduces each query to about log N switches instead of N; nothing in it makes filling the memory with N classical values cost less than N writes
B · It reduces both the query and the initial write to about log N
C · It reduces the number of oracle calls a search needs from the square root of N to log N
The 2008 design is about the memory call: n qubits of address, about log N switches per call. The N writes that put the data in are untouched, which is why caveat 1 survives it. The number of oracle calls is set by the search bound, not by the memory, so C confuses two different costs.

Aaronson closes his essay with a check to run on any proposed application. What are its two parts?

A · Is the qubit count high enough, and is the noise low enough
B · Is the speedup exponential, and has it been published
C · Does the application satisfy all of the fine print, and once the fine print is included, does a fast classical algorithm give the same information
The check is about the algorithm and its assumptions, not the hardware or the venue. Part (a) is the four caveats. Part (b) asks whether the same assumptions hand a classical algorithm the same speed, and session 4 is a published case where they did.

Cheat sheet

The skipped step. A quantum search over classical data starts with a load, and a load of N rows costs N writes.
Four caveats. Load the input fast, apply the matrix fast, keep it well conditioned, read the output in about n runs. Aaronson 2015.
His rule. A fast superposition AND no fast classical sampler for the same distribution. Both halves, or no exponential speedup.
The bridge. Loading a single 1 for free would beat the search bound Grover sits at, so a load of unknown data is order N.
qRAM. About log N switches per query (2008). It cuts the query and never the write.
One search. The load alone, N writes, is more than the N over 2 a scan needs. Brindle, constructed: 12,063,988 against 6,000,000 (load 1 per row, query cost log2 N, R = 1).
The window. Same model, 12,000,000 rows: quantum ahead of a scan from R = 3, behind a classical index beyond R = 4,224 searches per load.
The two-part check. (a) Is all the fine print satisfied? (b) With it included, does a fast classical algorithm give the same answer? Session 4 is (b).
