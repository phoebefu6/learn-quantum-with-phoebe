Part 0

The footnote gets a price

A square-root search is a real gain, measured on this page's register in session 5: 25 oracle calls against 512 lookups at 1,024 items. It is a gain on a search over data that is already loaded. A data team's data is never already loaded. It sits in tables on disk, and every row has to be written somewhere a quantum oracle can read it before the first query runs. This session puts a number on that write, sets it beside the search it was supposed to speed up, and finds the range of workloads where the trade comes out ahead.

★ What you walk out with today. A loading-tax function with three declared parameters (load per row, query cost, searches per load) that reproduces the page's engine to the last digit. The one-search row for Brindle's 12,000,000 constructed customers: 12,063,988 operations for the quantum path against 6,000,000 for brute force. The two crossing points across six dataset sizes, and the window between them. And a one-line answer to "when does the load not matter", which is: rarely, and you can say exactly when.

LiveThe slide with no load on it3 min▶

Speedup slides for search have one curve that climbs as N and one that climbs as the square root of N, and the gap between them widens to the right edge. Session 5 showed that this picture is correct about oracle calls. What the picture leaves out is the step before the first call: getting the rows into the machine. The question for today is not whether the square root is real. It is whether the square root survives the bill that arrives before it starts.

Real world

Brindle is a constructed retailer, and the vendor deck its board received is unnamed and constructed too. The deck's search slide had the two curves from session 5 and a box labelled "your data" with an arrow straight into the quantum side. The engineer circled the arrow and wrote one question beside it for the review: what does that arrow cost, per row, and who pays it each time the table changes?

Self-studyThe vocabulary, in loading terms3 min▶
  • Load. Writing N classical rows into a memory the oracle can query. One write per row at the very least, so order N, paid once per load.
  • QRAM. Quantum random access memory: a memory that can be addressed in superposition. A proposed architecture with a cost model on paper, not a component a data team can buy.
  • Query cost. What one oracle call costs once the oracle has to read that memory. The page's model sets it at log2 N, the switch count of the best proposed design.
  • Searches per load, R. How many searches run against one load before the data changes and has to be written again. The parameter that decides almost everything.
  • Classical index. A sorted list or hash built once in about N log2 N and then searched in about log2 N per lookup. The fair classical rival once R is large.
  • Crossing point. The value of R at which one path becomes cheaper than another. The model has two, and the honest claim lives between them.
Part 1 · covers what loading N rows costs

One write per row, before the first query

12 min live

The search in session 5 started from a register that already held the data. Here is the step that put it there. Every classical row is written once into a quantum memory, and the best proposed memory makes each later READ cheap without making that first WRITE any cheaper. The figure follows Brindle's customer table from disk to the oracle and writes the cost on each arrow.

LiveOrder N, and no way around it4 min▶

To search a table with an oracle, the oracle has to be able to see the table. For data that was born classical, which is every row a data team owns, that means writing each row into a memory the quantum circuit can address. However clever the memory, each of the N values has to arrive in it at least once, so the load is at least N writes. On Brindle's constructed 12,000,000-row customer table that is 12,000,000 writes before the first oracle call.

Set that beside the search it was meant to beat. A classical scan with no index needs N/2 lookups for a one-half chance, Grover's own figure, which is 6,000,000 on the same table. The load alone is twice the brute-force search. For a single search over fresh classical data the square-root gain is spent before it starts, and nothing about the search afterwards can buy it back.

Real world

In the review (Brindle and its people are constructed) the engineer wrote two numbers on the whiteboard, 12,000,000 and 6,000,000, and asked the room which one the vendor slide had drawn. It had drawn neither. The slide's quantum curve started at the first oracle call, which is like timing a delivery from the moment the van leaves the depot and leaving out the loading bay.

LiveQRAM is an assumption, not a device3 min▶

The memory in the middle of the figure has a name, quantum random access memory, and a well-known proposal behind it. A classical RAM uses n bits to address N = 2^n cells; a QRAM uses n qubits to address a superposition of cells. The proposal's contribution is the cost of a READ: its architecture needs about log N switches per memory call, rather than the N of a conventional design.

Giovannetti, V., Lloyd, S. and Maccone, L. (2008). Quantum random access memory. Physical Review Letters 100, 160501; arXiv 0708.1879.

Two things follow, and both go in the footnote. First, the cheap read is what the page's model uses for its query cost: log2 N per oracle call, 23.5 on Brindle's table. Second, nothing in the proposal makes the initial WRITE of N classical values cost less than N writes. The paper makes the read cheap. The load stays order N. And the memory itself is a proposed architecture: every claim that leans on it is a claim that begins "supposing it exists", and should say so.

Self-studyAaronson's fine print, caveat one3 min▶

Aaronson's essay lists four caveats that can each kill an advertised quantum speedup, and the first one is this session. The input has to be loaded fast, which needs a quantum RAM and a reasonably uniform vector; if preparing the input already takes a polynomial number of steps, the speedup vanishes "in the very first step". The essay is about exponential claims, where the stakes are larger, but the arithmetic is the same at the square-root scale: a gain that is smaller than the load is no gain.

Aaronson, S. (2015). Quantum machine learning algorithms: read the fine print. Nature Physics 11, 291-293.

A footnote in the same essay adds that the memory must be "passive". A memory that needs a processing element per stored number would also hand a classical parallel machine the same speed, so the comparison would no longer be quantum against classical. Read the two together and the rule is short: the load is part of the algorithm, and so is the memory that holds it.

Self-studyThe three parameters the model declares2 min▶

The page's engine prices the trade with a model small enough to read in one breath, and every number it prints is printed beside its three parameters.

  • Load per row. 1 write, the kindest possible value. Real loads can only cost more.
  • Query cost. log2 N per oracle call, one read of the proposed memory. Session 5's free oracle is the special case where this is 1.
  • Searches per load, R. How many searches share one load. 1 by default, because a table that changes has to be loaded again.

Around those three sit the fixed pieces: k = round(pi/4 sqrt N) oracle calls per search, N/2 lookups per brute-force search, and N log2 N once plus log2 N per search for a classical index. None of it is a hardware measurement. It is a declared model, and the point of declaring it is that anyone can move a parameter and watch the answer move.

LiveRead the one-search row first3 min▶

Leave the widget on its defaults: 12,000,000 rows, one search, load 1 per row, query cost log2 N. The quantum path costs 12,063,988 operations, of which 12,000,000 is the load and 63,988 is the search: 2,721 oracle calls at 23.5 each. Brute force costs 6,000,000. A classical index, built for this one search, costs 282,198,396, which is why nobody builds one for a single search. Brute force wins, and the margin is the load.

The search term is tiny. That is the square-root gain doing exactly what session 5 said it would, and it is why the quantum line in the figure is nearly flat. Everything about the quantum path at R = 1 is the load, and the load is twice the brute-force bill at every size in the sweep table: the ratio printed by the build-along is 2.0 on all six rows.

  • Set R to 2. Brute force still wins: two searches have not yet paid back one load.
  • Set R to 3. The quantum path wins for the first time. This is the first crossing.
  • Set R to 10,000. The classical index wins. This is the second crossing, and it is the one a slide leaves out.
LiveTwo crossings, and the window between them3 min▶

If one load can serve R searches, the quantum path beats brute force from R = 3 at every size from 10,000 rows up, and from R = 4 at 1,000 rows. That is the first crossing, and it is the one a speedup claim likes to quote. But a workload that searches the same table thousands of times is exactly the workload where a data team builds an index, and the honest rival at large R is the index, not the scan.

The index costs N log2 N once and log2 N per search, and past a certain R it is cheaper than the quantum path: past 37 searches per load at 1,000 rows, 118 at 10,000, 380 at 100,000, 1,211 at 1,000,000, 3,854 at 10,000,000 and 4,224 on Brindle's 12,000,000. On Brindle's table the window where quantum is the cheapest path is 3 to 4,224 searches per load, under the declared parameters. Move the query cost in the widget and both edges move; that is the parameter a claim most often leaves unprinted.

Real world

The engineer at constructed Brindle asked the data team two questions instead of one: how many searches run against the customer table between changes, and does an index already exist? The table is updated continuously, so every change is a new load and R resets. And the index existed already, built years ago for the website. The first answer pushes R toward 1; the second means the rival is the index, not the scan. Neither fact was on the slide.

Self-studyWhen the data is already quantum, or the oracle is cheap3 min▶

The load disappears in two situations, and both are real. The first is when there is no classical table at all: the input is a quantum state produced by another quantum process, such as a physical system being simulated. Preskill's survey of noisy intermediate-scale devices names exploring many-body physics as a place they should be useful, and in that setting nothing has to be written in row by row.

Preskill, J. (2018). Quantum computing in the NISQ era and beyond. Quantum 2, 79; arXiv 1801.00862.

The second is when the oracle computes its answer instead of reading it: a predicate that can be evaluated from the index alone by a circuit, with no stored rows behind it. Then the load term is zero and the query cost is the circuit's cost, which the model calls query cost. Set the widget's load to 0 to see this case: the quantum path wins from the first search. Watch the index column too, because even with a free load a classical index built once can still overtake a quantum search that is repeated often enough.

Self-studyWhy that is the exception3 min▶

A data team's tables are born classical: orders, customers, events, logs. Every one is rows on disk that would have to be written in, and every change to them is a new load. The cheap-oracle case is also rarer than it sounds, because "is this the row we want" usually means "read the row", which is the load again. So the two exceptions exist, and neither describes Brindle's customer table or its order table.

Aaronson states the general test: a big quantum speedup needs an extremely fast way to create the right superposition AND no fast classical way to create the analogous probability distribution. The load fails the first half for classical data. Leader session 4 covers the second half: when Tang gave a classical algorithm the same kind of preprocessed data structure the quantum recommendation algorithm assumed, the classical side caught up to within a polynomial.

Tang, E. (2019). A quantum-inspired classical algorithm for recommendation systems. STOC 2019; arXiv 1807.04271.

Part 3 · build-along

Build the calculator and read the crossings

20 min hands on

One file, five steps, run in order; each step uses what the one before defined. Plain Python, no numpy, and nothing is sampled, so every number is exact and yours will match the outputs below, which were printed by this exact code on Python 3.11. The function is the page's engine line for line, rounding included. Step 4 asserts the result equals the canon; if it raises, the build is wrong, not the canon.

The loading-tax function

Three declared parameters, five totals. k is round(pi/4 sqrt N) written as floor(x + 0.5), which is how the page's engine rounds; Python's own round() sends halves to the even neighbour and would disagree on the odd row. Print Brindle's one-search row first: the three totals must be the canon's.

Pythonimport math def loading_tax(N, R=1, load_per_row=1, query_cost=None): log2N = math.log2(N) q = log2N if query_cost is None else query_cost # one oracle call = one memory read k = max(1, math.floor(math.pi / 4 * math.sqrt(N) + 0.5)) # oracle calls per search per_search = k * q return dict(N=N, R=R, k=k, log2N=log2N, per_search=per_search, load=N * load_per_row, search=R * per_search, quantum=N * load_per_row + R * per_search, brute=R * N / 2, indexed=N * log2N + R * log2N) b = loading_tax(12_000_000) print(f"step 1: k = {b['k']:,} oracle calls at log2 N = {b['log2N']:.1f} each") print(f"quantum {b['quantum']:,.0f} = load {b['load']:,.0f} + search {b['search']:,.0f}") print(f"brute force {b['brute']:,.0f} | index {b['indexed']:,.0f}") # step 1: k = 2,721 oracle calls at log2 N = 23.5 each # quantum 12,063,988 = load 12,000,000 + search 63,988 # brute force 6,000,000 | index 282,198,396

One search, six sizes

Run the function across the six sizes in the canon, one search each, and print the load beside the brute-force bill. The last column is the whole of Part 1 in one number: the load alone is twice the brute-force search, at every size.

PythonSIZES = [1_000, 10_000, 100_000, 1_000_000, 10_000_000, 12_000_000] print(f"{'N':>11} {'load':>11} {'search':>7} {'quantum':>11} {'brute':>10} {'index':>12} load/brute") for N in SIZES: r = loading_tax(N) print(f"{N:>11,} {r['load']:>11,.0f} {r['search']:>7,.0f} {r['quantum']:>11,.0f} " f"{r['brute']:>10,.0f} {r['indexed']:>12,.0f} {r['load'] / r['brute']:.1f}") # N load search quantum brute index load/brute # 1,000 1,000 249 1,249 500 9,976 2.0 # 10,000 10,000 1,050 11,050 5,000 132,890 2.0 # 100,000 100,000 4,119 104,119 50,000 1,660,981 2.0 # 1,000,000 1,000,000 15,646 1,015,646 500,000 19,931,589 2.0 # 10,000,000 10,000,000 57,762 10,057,762 5,000,000 232,534,990 2.0 # 12,000,000 12,000,000 63,988 12,063,988 6,000,000 282,198,396 2.0

Find the two crossings

Each extra search saves N/2 minus the quantum search cost against brute force, so the load is paid back after the load divided by that saving, rounded up. Each extra search costs the quantum search minus log2 N against the index, so the index's head start runs out after its build minus the load, divided by that, rounded down. Read the window off each row.

Pythondef crossings(N, load_per_row=1, query_cost=None): r = loading_tax(N, 1, load_per_row, query_cost) gain = N / 2 - r["per_search"] # what each search saves against brute force lag = r["per_search"] - r["log2N"] # what each search costs against the index beat_brute = math.ceil(N * load_per_row / gain) if gain > 0 else None index_past = None if lag > 0: index_past = max(0, math.floor((N * r["log2N"] - N * load_per_row) / lag)) return beat_brute, index_past print(f"{'N':>11} beats brute force from R index wins past R") for N in SIZES: lo, hi = crossings(N) print(f"{N:>11,} {lo:>23} {hi:>17,}") # N beats brute force from R index wins past R # 1,000 4 37 # 10,000 3 118 # 100,000 3 380 # 1,000,000 3 1,211 # 10,000,000 3 3,854 # 12,000,000 3 4,224

Assert the canon

Both crossings on all six sizes, and Brindle's one-search total, against the frozen canon. If either assertion raises, stop and find the bug before quoting anything; the usual culprit is Python's round() in step 1.

Pythoncanon = {1_000: (4, 37), 10_000: (3, 118), 100_000: (3, 380), 1_000_000: (3, 1_211), 10_000_000: (3, 3_854), 12_000_000: (3, 4_224)} for N, want in canon.items(): assert crossings(N) == want, (N, crossings(N), want) assert round(loading_tax(12_000_000)["quantum"]) == 12_063_988 print("matches canon: six sizes, both crossings, Brindle's one-search total") # matches canon: six sizes, both crossings, Brindle's one-search total

Turn a knob and read the window move

The query cost is the parameter a claim most often leaves unprinted, so sweep it. These numbers are not in the canon and the page does not quote them; set the widget above to the same query cost and the same load and its sweep table will print the same crossings. Notice which edge of the window moves, and the sizes where quantum never beats brute force at all.

Pythonknobs = [("free oracle, 1 per call", lambda N: 1), ("ten reads a call, 10 x log2 N", lambda N: 10 * math.log2(N))] for label, cost in knobs: print(label) for N in SIZES: lo, hi = crossings(N, query_cost=cost(N)) print(f" {N:>11,} beats brute force from {lo} index wins past {hi}") # prints two sweeps of six rows each; set the widget's query cost to match and its sweep table agrees

The habit to keep. Never quote a search speedup without its load. Print the one-search row, then the two crossings, then the three parameters they rest on: "beats brute force from 3 searches per load, loses to an index past 4,224, at load 1 per row and query cost log2 N". A speedup with no load term is a slide; with it, it is a model someone can check.

Check yourself

Three questions

For one search over Brindle's 12,000,000 constructed rows, the model prints 12,063,988 operations for the quantum path against 6,000,000 for brute force. Why does the quantum path lose?

A · Because 2,721 oracle calls is more than the 6,000,000 lookups brute force needs
B · Because the load alone is 12,000,000 writes, twice the brute-force search; the search itself adds only 63,988
C · Because the simulator stops at ten qubits, so a 24-qubit search cannot be priced
The square-root gain is intact: 2,721 calls at 23.5 each is 63,988. What loses is the load, one write per row, paid before the first call and twice the N/2 lookups brute force needed. The loading tax is a declared model, not a simulation, so the ten-qubit limit does not apply to it.

The model says the quantum path beats brute force from 3 searches per load on Brindle's table. What is the honest next sentence?

A · So the pilot should be sized for three searches
B · So quantum wins for every workload with three or more searches per load
C · But a workload with many searches per load is exactly where a classical index is built, and the index overtakes the quantum path past 4,224 searches, so the window is 3 to 4,224 under load 1 per row and query cost log2 N
The first crossing compares against a brute-force scan that nobody runs thousands of times. The second compares against an index, the fair rival at large R. Both edges move when the query cost or the load per row moves, which is why the parameters go in the sentence.

What does the Giovannetti-Lloyd-Maccone quantum RAM proposal change about the loading tax?

A · It makes one query cost about log N switches instead of N; it does nothing to make writing N classical values cost less than N writes, and it is a proposed architecture
B · It makes the load cost log N instead of N, which removes the loading tax
C · It removes the need for an oracle, so a search costs one call
The proposal is about the READ: a memory call through log N switches. The page's model uses that for its query cost, 23.5 on 12,000,000 rows. The WRITE of N rows stays order N, and every claim that relies on the memory relies on a design, not a device.

Cheat sheet

The memory. QRAM is a proposed architecture. Its read costs about log N switches; its write of N values still costs N.

The ratio. Load over brute force is 2.0 at every size: one search never pays the load back.
First crossing. Quantum beats brute force from R = 3 searches per load (R = 4 at 1,000 rows).
Second crossing. A once-built index beats quantum past R = 37 at 1,000 rows, up to 4,224 at 12,000,000.
The parameters. Load 1 per row, query cost log2 N, R searches per load, k = round(pi/4 sqrt N). Print them beside every number.
